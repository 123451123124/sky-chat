## 相对前一版新增的技术能力

### 权限：资源级约束，不只检查登录角色

知识库可选择仅所有者、指定用户组及子组、所有登录账号。GroupClosure 保存祖先/后代关系，避免每次检索都由客户端上传院系路径。成员身份来自数据库，不放进长期 JWT。

文件支持继承、仅所有者、限定用户/用户组。文件范围进一步收紧知识库范围，读取需同时满足库级和文件级授权；所有者保留访问自己文件的能力。指定账号不会绕过私有库或非所属组的库级限制。

全文和向量 SQL 都包含同一资源权限条件，再执行排名和候选限制。API 列表、原文、下载、父块回填和历史版本也执行权限检查。成员移除与管理员降权无需重新签发 JWT 即可生效。收紧文件权限同步作用于历史版本。

已经收到的回答、摘录或下载无法远程收回；撤销的是新的检索和原文读取权限。

### 分块：结构、语义与父子上下文

默认按页码/Markdown 标题分节，再用 LangChain 递归切为父块与子块。父块约 1800 个 Unicode 字符，子块约 480，重叠 60；中文标点和段落优先，兜底不会截断 UTF-16 代理对。这是字符预算，不冒称精确模型 Token 分词。

可选语义策略：先切出短段，对相邻向量距离计算分位边界，并结合长度上限形成父块，再切检索子块。语义策略确实调用已配置的向量服务，不是把普通定长切分重新命名。其额外开销在任务指标中保留。

检索命中子块后，经授权读取父块，去除同父重复结果，并保留被命中的子块 ID。模型引用指向实际回填的父块，查看原文时不会出现“引用的是子块，结论却只在别处”的定位错配。

### 检索：多路召回、可选模型重排与降级

使用 ICU 中文分词、未登录词二元片段和完整编号构造全文索引，PostgreSQL GIN/tsvector 召回与 pgvector 召回并行。两路不同量纲的分数不直接相加，而是使用 RRF 排名融合。

再调用阿里云真实 `qwen3-rerank` 排序，按父块去重和文档多样性选取上下文。支持标签交集筛选。查询向量请求受时间预算约束；向量服务失败可保留全文候选，重排失败保留融合排序并显示降级原因。

当前关键词排序使用 `ts_rank_cd`，**不是 BM25**；向量侧仍是授权范围内的精确余弦排序，未声称已实现 HNSW 大规模 ANN 或 Elasticsearch。不能根据功能列表声称整体性能优于对照项目。

### 入库：检查点、租约防护、重试和死信

PostgreSQL 队列使用 SKIP LOCKED 领取任务、唯一租约令牌和心跳；阶段更新与最终写入校验租约，防止失效 worker 覆盖结果。父子块及向量在事务中原子替换。

解析结果保留检查点；成功的向量批次独立入缓存，后续批次失败后可以复用。瞬态错误有退避和最多三次任务尝试，永久错误或次数耗尽进入 dead；管理页面提供人工重试。恢复时不叠加旧分块。

这是持久数据库队列和死信状态，不是 Kafka，也没有把 p-queue 当成持久任务队列。

### 向量化：并发之外还处理成本、隐私与传输

向量批次最多 10 条，同一进程默认最多 3 个请求；worker 默认同时处理 2 个文件。窗口速率、请求并发和文件并发分别配置。429 按 Retry-After/指数退避，降低并发后逐步恢复；单条查询可优先于大文件批次。输出按输入顺序还原。

重复输入按内容哈希去重。缓存键含账号、模型/地址/维度及文本哈希，跨账号不共享私有缓存命名空间。进程内缓存最多 1024 个 Float32 向量，10 分钟 TTL；数据库缓存 30 天 TTL，由 worker 定期清理到期项。数据库向量用 pgvector 二进制表示读取，避免冗长十进制 JSON。删除文件会清理该所有者的持久缓存和当前 Web 进程缓存；其他进程的内存副本由 TTL 淘汰，任何后续资料访问仍受资源权限约束。

并发/限速是**进程内**的，多进程部署需按服务商总配额分摊配置，不能声称已经实现分布式全局限流。

### 文档版本：先验证成功，再切换当前版本

管理员可上传新版本，原文件与片段按独立版本保留。新版本处理成功后事务切换当前标记并迁移会话选择；失败时旧版继续可用，失败版可以单独重试或删除。旧回答继续定位原有来源。

移动文件、收紧访问或删除文件按整个版本家族处理。单独删除未启用/历史版本会明确告知，当前版本不能通过该入口被误删。

### 可观测与评测：把技术点变成可复核的证据

管理端提供分块预览、任务尝试/错误、文件与版本权限、分路候选数量、父块回填、向量缓存和阶段耗时。聊天的检索记录也能显示实际检索策略与降级。

固定数据集位于 `tests/fixtures/retrieval-corpus.ts`：8 份虚构政策、42 个标注问题，含编号、条件否定、相似规则和跨文档比较。运行 `npm run rag:evaluate`，比较向量、混合、混合＋重排，保存全部逐题结果。

最终复测：三路文档级 Recall@5 都为 1；MRR 分别为向量 0.964、混合 0.988、混合＋重排 1.000。P50 分别为 700、1029、1197 ms，P95 为 1480、1829、2211 ms。查询向量预热、策略顺序轮换，本轮与工程冒烟并行运行，耗时包含远程数据库及同机负载。前次混合 MRR 曾达到 1.000，说明这组小样本存在运行波动，不能宣称重排总有收益。它不是公开基准、答案准确率或业务规模保证；不会为了展示效果删掉不利结果。

真实向量请求基准见 `reports/embedding-benchmark.json`，保留三轮原始耗时、串行/并发顺序与冷热缓存请求数。它只测向量请求阶段和缓存路径，不能写成整个 RAG 系统吞吐提高同等比例。

## 复现入口

```powershell
npm test
npm run test:e2e
npm run rag:evaluate
npx tsx scripts/embedding-benchmark.ts
npx tsx scripts/rag-engine-smoke.ts
```

后两类真实服务验证需要已启动的 Web/worker，使用虚构文件与独立临时账号，并在结束后清理。模型调用会消耗当前供应商配额。部署与文件格式边界继续见 [RAG使用与部署.md](RAG使用与部署.md)。
