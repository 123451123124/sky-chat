## 推荐采用的 RAG 产品设计

[Open WebUI 官方入门文档](https://github.com/open-webui/docs/blob/main/docs/getting-started/essentials.mdx) 清楚区分会话附件和长期知识库，适合尚未确定业务场景时采用。

### 会话附件

拖入 PDF、Markdown 或 TXT，展示文件处理状态；处理完成后，后续提问只检索这段对话关联的文件。可一次选多个文件进行问答或比较。元数据与向量仍持久化，刷新后不用重新上传；“会话范围”不是只在浏览器内存保存。

### 可复用知识库

资料整理到用户自己的知识库，开启新对话时显式选择。文件只入库一次，更新时按版本重建受影响分块；移除文件后清理关联向量。知识库不是固定行业模板，可以存论文、产品手册、学习材料或公开项目文档。

### 共享底层链路

上传 -> 持久化处理任务 -> 解析并保留定位信息 -> 切分 -> Embedding -> pgvector -> 按授权范围召回 -> 可选重排 -> 带来源的回答。

首版支持单文件与多文件选择、处理状态、失败重试、引用查看和删除。扫描件 OCR、网页抓取、复杂表格识别、搜索调参面板后置；支持格式、文件上限与解析限制应在界面如实展示。

## 适合当前项目的数据与服务边界

[LibreChat RAG API](https://github.com/LibreChat-AI/rag-api) 使用 file_id 定位文档向量，并在查询前按调用者范围过滤。Sky Chat 可以借鉴这个边界，保留自己的 Node 实现，不必为采用同一思路而引入 FastAPI/LangChain。

- Document：原文件、所有者、版本、处理状态、哈希。
- Chunk：片段正文、页码/标题、模型版本、向量及所属文档。
- KnowledgeBase / 关联表：哪些文档属于哪个知识库。
- SessionDocument / SessionKnowledgeBase：当前会话允许检索哪些资源。
- IngestionJob：等待、处理、完成、失败，含重试与幂等信息。

检索入口接收用户选择的资源 ID；服务端重新验证访问权限，并在向量查询前限定范围。不要接受模型生成的 userId 作为查询身份。所有文件和知识库复用同一检索服务。

引用保存为结构化数据：来源类型、documentId、chunkId、文件名、位置与片段。模型输出的引用 ID 必须属于本次召回，不只依赖模型自己生成网址或文档名。

## 围绕 RAG 的适度 Agent 增强

以下是结合当前 Sky Chat 代码提出的实现建议，不是上述项目已经验证过的效果，也不代表这些功能已经在 Sky Chat 中实现。

现有服务已有最多 5 轮模型/工具循环，可以新增两个内置只读工具：`searchKnowledge` 检索已选资料，`readDocument` 读取授权片段及有限上下文。直接复用内部 RAG 服务，不增加外部工具协议层。

1. 结合近期对话，把代词、省略较多的追问改写为独立检索问题。
2. 跨文件比较或多问问题最多拆成 3 个子问题，合并去重检索结果。
3. 首次证据不足时可换词检索或读取相邻片段，首版最多 2 轮检索；仍不足则说明缺失信息。
4. 所有检索受服务端身份和用户显式选择的文件/知识库约束，模型不能扩大范围。
5. 限制总模型轮数、工具次数、耗时与上下文，重复调用复用结果，预留最终回答机会。
6. 保存并折叠展示检索操作、来源及耗时；不展示内部思维链，不承诺请求断开后自动续跑。

没有选资料时继续普通聊天。选择资料后，文档回答必须建立在实际检索结果上；低相似度不等于确定无答案，高相似度也不保证答案正确。补查需要用同一组题与单次检索进行对照，证明额外步骤带来实际收益。

## 推荐先做的页面变化

- 保留现有云白编辑台的会话导航、模型切换和输入布局。
- 上传后增加“处理中/可检索/失败”状态，展示该会话的检索文件范围。
- 提供一个轻量文件/知识库管理页，支持重试、删除、选择。
- 回答下显示来源入口，展开后看到片段和页码/标题定位。
- 检索操作折叠展示，区分首次检索与补查，记录实际耗时。
- 区分“检索到的资料”与“回答引用的资料”，验证引用 ID，不把任意模型输出当成真实来源。

## 首版交付判断

普通聊天不受额外功能影响；上传文件后能跨轮问答且来源可核查；知识库可跨对话使用且权限隔离；Agent 能在限定预算内理解追问、补查或说明证据不足；失败可恢复。先完成这些能力，再按评测结果决定是否加入混合检索与重排。
